# Portfolio proposals

Pull the update and restart the backend and dashboard. No dependencies, credentials or paid services have been added.

1. Open **Leads → Portfolio & proposals · TS Industries**. The starter catalogue contains `https://ts-industries.co.za/`, `https://rbptech.co.za/` and `https://rhymamusic.co.za/`, supplied by the operator. Site availability and project features have not been verified by this implementation.
2. Add descriptions only for work you delivered and features you can substantiate. Descriptions appear in outgoing proposals. Optional comma-separated industry tags match whole words/phrases in a lead's saved industry. For example, add `music` only if the project is relevant to that industry. No industry tags or feature claims are inferred from a domain name.
3. Save the catalogue. You can add/remove up to 12 projects or disable examples. Matching selects up to two active examples, prioritizing matches and explaining each selection. If no tags match, the first two active projects are general examples. With none active, only the agency portfolio is included. The saved catalogue persists in the local SQLite ledger and overrides the starter JSON; keep database backups. A concurrent edit returns a conflict; reload before saving again.
4. Select a candidate. Complete its identity, current activity, website-absence research and exact contact review. Record genuine contact permission separately in Settings. Existing-website, inactive, stale, unreviewed or suppressed contacts remain blocked. Research assessments and published emails do not establish permission.
5. Click **Generate portfolio proposal**. This creates a saved preview and fills the subject/message fields. It uses local templates and data, with no model, memory-provider, research or Gmail request. The connected mailbox must be configured. The message includes the supplied portfolio/examples, cautiously describes website research, asks to discuss scope before a quotation, includes the existing business email/phone signature and a reply-unsubscribe instruction. It makes no pricing, revenue or performance claims.
6. Edit the subject and body, then click **Save for approval**. If the lead review, mailbox or portfolio changed since generation, regenerate first. Manual drafting is still available without generation. The queued record preserves the selected project snapshot and whether text was edited before queueing. Later catalogue changes do not rewrite saved approvals.
7. Open **Approvals**, review the actual saved recipient, subject and message, then explicitly approve sending. Existing Gmail eligibility and last-moment evidence checks still apply. Editing the body in Approvals changes what is sent. A project-source snapshot documents the initial composition; it does not certify the current text or website availability.

One initial outreach record per connected mailbox/contact is retained. Repeated generation creates previews, not duplicate messages. Repeated queueing never replaces an existing approval, including one already sent. Use the existing conversation/history workflow instead of creating repeated initial outreach. Human unsubscribe replies are processed by the existing sync/suppression workflow; the footer is not a tracking or unsubscribe link.

The core outreach graph uses the same local proposal service and queues its results for approval. Research jobs continue to discover/inspect/assess only. They do not generate or send proposals. This is the proposal-composition portion of Phase 5; automated reply interpretation, follow-ups and campaigns are not implemented here.

Private API routes: `GET/PUT /api/portfolio`, `POST /api/leads/{id}/proposal`, and the existing `POST /api/leads/{id}/draft` with optional `proposal_preview_id`. Existing API-key configuration applies. Stored previews bind the lead revision, reviewed recipient, catalogue version and mailbox. Tests use isolated fixtures and fake providers; no real business was emailed for validation.
